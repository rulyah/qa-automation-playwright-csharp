# QA Automation — Playwright + C#

Навчальний, але робочий набір автотестів: UI-тести e-commerce-магазину та CRUD-тести REST API.
Мета проєкту — не покрити застосунок, а показати **підхід**: як структурований фреймворк, чому тести стабільні й чому зі звіту про падіння зрозуміло, що зламалось.

**Стек:** C# / .NET 9 · Playwright 1.62 · NUnit 4 · json-server (мок-API)

## Як запустити

### API-тести — працюють у будь-кого

Потрібен [Node.js](https://nodejs.org) і [.NET 9 SDK](https://dotnet.microsoft.com/download).

```bash
# 1. підняти мок-сервер (окреме вікно, лишити працювати)
cd mock-api
npm install
npm start                      # http://localhost:3000

# 2. прогнати тести
dotnet test --filter "Category=RestApi"
```

Тести самі створюють потрібні дані й прибирають за собою, тому `db.json` можна не готувати — достатньо, щоб сервер відповідав. Якщо сервер не піднятий, тест упаде з підказкою, що саме зробити, а не з мережевою помилкою.

### UI-тести — потрібен локальний LiteCart

```bash
dotnet test --filter "Category=Checkout"
```

За замовчуванням тести йдуть на `http://localhost/litecart/`. Інший стенд задається змінною середовища, код міняти не треба:

```powershell
$env:LITECART_BASE_URL = "http://example.com/shop/"
dotnet test --filter "Category=Checkout"
```

Перший запуск потребує браузерів Playwright:

```bash
dotnet build
pwsh bin/Debug/net9.0/playwright.ps1 install chromium
```

## Технічні рішення

**Компоненти, а не лише сторінки.** Кошик і блок акаунта присутні на всіх сторінках. Якби вони жили в `HomePage`, `ProductPage` і `CheckoutPage` окремо, будь-яка зміна верстки кошика означала б правку в трьох місцях. Винесені в `Components/` зі спільним `BaseComponent` — одна зміна, одне місце.

**Асерт як точка синхронізації.** Замість очікувань на кшталт `WaitForSelector(":not(:empty)")` використовується `Expect(...).ToHaveTextAsync("1")` — веб-перший асерт Playwright сам перечікує оновлення DOM. Це водночас і синхронізація, і перевірка; `Thread.Sleep` у проєкті немає.

**Конфігурація відокремлена від коду.** `TestConfig` читає `LITECART_BASE_URL` зі змінної середовища з локальним значенням за замовчуванням. Переведення набору на інший стенд — це змінна оточення в CI, а не коміт.

**Кожен API-тест готує свої дані сам.** Тести не читають те, що лежить у `db.json`, а створюють власні записи з унікальними іменами й реєструють їх на видалення. Наслідок: тести можна запускати поодинці, разом, повторно і в будь-якому порядку — вони не залежать ні від стану бази, ні один від одного.

**Прибирання в `TearDown`, а не в кінці тесту.** `TearDown` виконується і після падіння. Якщо асерт упав посередині — створені записи все одно приберуться, і наступний прогін почнеться з чистого стану.

**Перевіряється наслідок, а не код відповіді.** `DELETE` повернув `200` — це лише «сервер прийняв запит». Те, що запис справді зник, доводить наступний `GET`, який має повернути `404`.

**Негативні перевірки і незмінені поля.** Для `PATCH` найважливіша частина асерту — поля, яких ми *не* чіпали: без них тест пройшов би й тоді, коли `PATCH` затер решту даних. Окремий тест фіксує семантику `PUT` — він замінює ресурс цілком, і пропущені поля зникають.

**Повідомлення про падіння містить причину.** `ShouldHaveStatusAsync` показує у звіті статус, URL і тіло відповіді. Голий `Assert.That(status, Is.EqualTo(200))` каже «очікували 200, було 500» — далі доводиться лізти в логи сервера.

**Імена тестів за схемою `Метод_Умова_ОчікуванийРезультат`.** Зі списку впалих тестів видно, що саме зламалось, без відкривання коду.

## Обмеження

- **UI-тести не запустяться без локального LiteCart** — це навчальний стенд, публічного інстансу немає. API-тести відтворюються повністю: `mock-api` лежить у репозиторії.
- `.runsettings` налаштований на **демонстраційний** режим: `Headless=false`, `SlowMo=700`, один воркер — щоб за прогоном було видно, що відбувається. Для CI це перемикається на headless і паралельний запуск.
- Покриття навмисно вузьке: один наскрізний UI-сценарій і один ресурс API. Проєкт показує структуру й підхід, а не повноту.
