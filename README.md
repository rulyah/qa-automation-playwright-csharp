## API-тестування в Postman

Колекція `LiteCart` тестує додавання товару в кошик через `POST /ajax/cart.json` — той самий запит, який надсилає сторінка товару (знайдений через DevTools → Network).

| # | Запит | Що перевіряє |
|---|---|---|
| 1 | **Get CSRF token** — `GET /litecart/` | Дістає CSRF-токен поточної сесії з HTML сторінки (`_env`) і кладе в змінну `csrf_token`. Тест: токен знайдено |
| 2 | **Add to cart — negative quantity** — кількість `-1` | Сервер повертає `alert: "Invalid item quantity"` **і** кількість товару в кошику не змінилась |
| 3 | **Add to cart — valid** — кількість `{{add_qty}}` | У відповіді немає `alert` **і** кількість зросла рівно на додане |

Як побудовано:
- **Кореляція токена.** LiteCart відхиляє POST без токена сесії (`403 CSRF token mismatch`). Токен не захардкоджений: запит 1 дістає його щоразу, а запити 2–3 беруть зі змінної. Кука сесії `LCSESSID` іде автоматично з банку кук Postman.
- **Стан «до» в pre-request.** Перед POST скрипт окремим `GET /ajax/cart.json` запам'ятовує поточну кількість товару (`qty_before`), щоб перевіряти не просто «немає помилки», а точну зміну кошика.
- **Перевіряється тіло, а не статус.** Помилки LiteCart повертає з кодом `200`, текст помилки лежить у полі `alert`. Тому тест на статус пройшов би й на невдалому додаванні.

Запуск: відкрити теку `postman/` у Postman як локальний робочий простір, у змінних колекції задати `product_id` = `4`, `add_qty` = `1` і прогнати Collection Runner у порядку 1 → 2 → 3. Потрібен локальний стенд LiteCart (див. нижче).

## Тестовий стенд

Для навчання я підняв власний стенд; під нього написані і UI-тести, і ручне тестування.

- **Магазин:** LiteCart 2.7.0, локальна інсталяція на XAMPP (Apache, PHP 8.2.12, MariaDB 10.4.32), Windows 10.
- **Налаштування середовища:** щоб магазин запрацював, довелося ввімкнути PHP-розширення `intl` і розібратися з часовим поясом магазину. Обидві проблеми спершу були знахідками і описані як дефекти в [`docs/BUG-REPORTS.md`](docs/BUG-REPORTS.md) (LC-1, LC-10).
- **Тестові дані:** база магазину частково змінена вручну під конкретні сценарії: залишки, статуси товарів, тестові замовлення.
- **API:** мок-сервер [json-server](https://github.com/typicode/json-server) з каталогу `mock-api/`.
- **Інструменти:** Chrome DevTools (Network, Console), phpMyAdmin і SQL-запити для перевірки стану бази.
